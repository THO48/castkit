# LANCast v1 — CastKit 安卓投屏协议

**用途**：CastKit 发送端（`com.dsh.castkit.sender`）→ 接收端（`com.dsh.castkit.receiver`）的局域网投屏。
iOS 走原生 AirPlay（UxPlay），不使用本协议。

**设计取舍**：只用一条 TCP 连接，服务端监听，客户端主动接入。不引入 RTP/RTCP/RTSP：
两端都是我们自己的代码，TCP 已保证有序可靠，省掉 RTSP 服务端实现（Android 上没有现成的、
可嵌入的 RTSP *服务端*）与 RTP 乱序/丢包处理；所有字节序为小端。

```
默认端口 TCP 8123                     ┌──────────────┐
发送端 (client) ──── 握手 24B + CSD ──▶│  接收端      │
                ◀── ready / keyframe 请求│ (server)     │
                ──── 帧循环 ───────────▶│              │
```

## 1. 握手（客户端 → 服务端，24 字节 + CSD）

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | u8[8] | magic | `"LCAST1\0\0"`（0x4C 0x43 0x41 0x53 0x54 0x31 0x00 0x00） |
| 8 | u16 | width | 视频宽（像素） |
| 10 | u16 | height | 视频高（像素） |
| 12 | u16 | fps | 目标帧率 |
| 14 | u8 | videoCodec | 1 = H.264/AVC（当前唯一取值） |
| 15 | u8 | flags | bit0 = 含音频轨 |
| 16 | u32 | bitrateBps | 目标码率（bit/s，仅信息性，供接收端展示） |
| 20 | u16 | csdLen | 视频 CSD 字节数（0 表示后续用 `type=0` 帧发送） |
| 22 | u16 | rsv | 保留，填 0 |
| 24 | u8[csdLen] | csd | 见下 |

**CSD 编码**：`u16 spsLen | SPS | u16 ppsLen | PPS`（取自 MediaCodec `outputFormat` 的 `csd-0`/`csd-1`）。

握手超时 10 秒；magic 不符或版本不支持时服务端直接关闭连接。

## 2. 服务端 → 客户端（控制消息）

单字节 `type`：

| 值 | 含义 | 后续字节 |
|---|---|---|
| 0 | `ready` | 无（客户端收到后开始推帧） |
| 1 | `request-keyframe` | 无（客户端下一次编码强制 I 帧） |
| 2 | `bye/error` | u8 错误码：1=协议错误 2=不支持 3=忙（已有会话） 4=内部错误 |

## 3. 帧（客户端 → 服务端）

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | u8 | type | 0=视频 CSD，1=视频 AU，2=音频 CSD，3=音频 AU，4=ping，**5=改分辨率**，**6=投视频地址**，**7=结束投视频** |
| 1 | u8 | flags | bit0 = 关键帧（仅 type=1/3 有意义） |
| 2 | u16 | rsv | 0 |
| 4 | u32 | ptsUs | 展示时间戳（微秒，编码器输出时间基） |
| 8 | u32 | len | 负载长度 |
| 12 | u8[len] | payload | H.264 访问单元 / AAC 帧 / CSD；type=6 时是 UTF-8 的 `http(s)://` 地址 |

- 视频 CSD 帧（type=0）的 payload 与握手里的 CSD 编码一致；**CSD 变更（分辨率变化）时必须重发 CSD 帧**。
- **`type=5`（改分辨率）**：payload = `u16 width | u16 height`，用于手机旋转等中途改变分辨率；
  发送端必须先发该帧、紧跟一帧 `type=0` 的 CSD；接收端收到后释放解码器并按新尺寸重建、再请求关键帧。
  旧接收端对该类型天然忽略（帧类型分支的 else），因此向后兼容。
- **比例约定**：发送端始终发送"与手机屏幕同比例"的帧（预设 = 短边像素，长边按屏幕长宽比推算，
  16 对齐）；接收端一律用**流本身的 width/height** 给视频 Surface 定比例，不足处留黑边，不做拉伸。
- `ping` 帧（type=4）无负载，服务端可忽略；用于空闲保活（客户端每 5 秒发送一次，服务端 15 秒无帧则断开）。
- 单帧上限 8 MiB（超过视为协议错误）。

## 4. 会话与恢复

1. 接收端同一时刻只接受 1 路 LANCast 会话；已有会话时回 `bye(3)`。
2. 接收端开始 AirPlay 镜像或用户停止时，关闭当前 LANCast 会话（客户端收到 EOF 后停止采集）。
3. 客户端断连后重试 3 次（1s/2s/4s 退避）；期间前台服务保持，UI 显示重连状态。
4. 丢关键帧导致花屏时，服务端发 `request-keyframe`；客户端在 `MediaCodec` 下一次 `dequeueInputBuffer` 后
   用 `requestKeyFrame()`（`MediaCodec.PARAMETER_KEY_REQUEST_SYNC_FRAME`）触发 I 帧。

## 5. 设备发现（UDP 8124，已实现）

发送端打开界面即开始搜索，**用户不需要输入 IP**：

```
发送端 ──每 3 秒──▶ 255.255.255.255:8124 以及各网卡子网广播地址
                    "LCAST1-PROBE\n"
接收端 ──单播回────▶ 发送端所在端口
                    "LCAST1-HERE <tcpPort> <名称>\n"
接收端 ──每 5 秒──▶ 255.255.255.255:8124（便于先启动的发送端直接看到）
```

- 名称取接收端设置里的「设备名称」（默认 `Android AirPlay`），换行会被替换成空格。
- 发送端把 15 秒内收到过消息的接收端列出来（按 `host:port` 去重），自动选中第一个；
  用户也可以点「重新搜索」立即再探测一次，或展开「手动输入地址」填 `IP:端口` 兜底。
- 两端都持一个 `WifiManager.MulticastLock`，避免 Wi-Fi 省电把广播/组播过滤掉；
  发送端需要 `CHANGE_WIFI_MULTICAST_STATE` 权限（已声明）。
- 发现只在接收端开启「接收 CastKit 发送端投屏」时生效（接收端 UDP 8124 监听 + 周期广播）。
- 失败兜底：若 AP 禁止客户端互播（AP isolation），仍可用「手动输入地址」。

## 6. 兼容性

- `videoCodec`、`flags`、`type` 都是枚举，新增值需要同时升级两端；`version` 由 magic 尾部两位承载，
  当前为 `1`（握手 magic 固定 8 字节，破坏性改动时递增尾字节）。

## 7. 投视频文件（v1.1，type=6 / 7）

发送端不想（或不需要）镜像整屏时，可以只把**一个视频文件**交给接收端播：

1. 发送端用内置的单文件 HTTP 服务（默认 8130，支持 `Range`）在局域网暴露该文件；
2. 照常建立 LANCast 连接并完成握手（`width=height=fps=0`，本模式没有视频帧）；
3. 收到 `ready` 后发送一帧 `type=6`，payload 是形如
   `http://192.168.1.5:8130/v/movie.mp4` 的地址；
4. 接收端用**系统原生播放器**直接访问该地址播放（原始码流、原画质、有声音、可拖进度），
   期间只靠 `type=4` 心跳维持会话（接收端 15 秒空闲会断连）；
5. 用户点停止时发送端发一帧 `type=7`，然后关闭连接。**连接意外断开不发 7**，
   这样网络抖动不会打断接收端正在播放的画面。

两种模式的区别：镜像模式推 H.264 访问单元（`type=1`），投视频模式一帧视频都不推；
接收端按是否收到 `type=6` 走不同的播放管线，互不干扰。

**会话中再次收到 `type=6` = 换片**（v1.3 补）：发送端播放页点「上一个 / 下一个」时**不结束会话**，
只把 HTTP 服务正在暴露的文件换成新片、再发一帧 `type=6`。接收端收到后释放当前播放器、改播新地址
（`LanVideoPlayer.play()` 内部先 `releaseInternal()`），**心跳、遥控、状态回报全部沿用同一个会话**，
不需要重连；新地址的 `type=6` 之后若还带 `type=8`（seek）就照旧生效（换集一般不带，从 00:00 播）。
这套约定不改任何帧格式，因此 1.0.1 的发送端与更早的接收端也能互通（对面若忽略第二次 `type=6`，
它会继续播旧片）。

## 8. 投屏遥控与状态回报（v1.2）

投视频文件时发送端不只下发地址，而是当**遥控器**用：进度条显示接收端真实进度，拖动即同步 seek。

### 8.1 发送端 → 接收端：`type=8`（控制）

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | u8 | action | 1=播放 2=暂停 3=切换 4=seek |
| 1 | u32 | value | seek 时为毫秒，其它填 0 |

帧头照旧（12 字节），负载固定 5 字节。

### 8.2 接收端 → 发送端：`0x7F` 扩展消息

原有反向通道只发**裸控制字节**（`ready`/`request-keyframe`/`bye`）。状态回报是结构化数据，
因此约定 `0x7F` 为扩展前缀：

```
0x7F | u16 len | payload[len]     payload[0] = 消息类型
```

| 类型 | 名称 | 负载 |
|---|---|---|
| 9 | `status` | u32 位置ms · u32 时长ms · u8 flags（bit0=播放中 bit1=缓冲中） |
| 10 | `stop` | 空（接收端用户在本机点了「断开投屏」） |

接收端在投视频会话中**每秒**回报一次；control 字节与扩展消息写同一个输出流，用同一把锁保证不交错。

`stop`（v1.2 补）解决的是"接收端断不干净"：没有它时，接收端按返回只能停掉自己的播放器，
发送端要等 **8 秒**收不到 `status` 才自己收尾（`RECEIVER_IDLE_TIMEOUT_MS`），期间一直显示"投送中"、
HTTP 文件服务与前台通知都还挂着。收到 `stop` 后发送端立刻 `teardown` 并 `stopSelf`。
接收端只发消息、不主动关连接 —— 连接由发送端收尾时关掉；对面若是忽略该消息的旧版本，
仍会走原来的 8 秒超时兜底。

**实现注意（踩过的坑）**：`stop` 是用户在接收端点按钮 / 按返回触发的，也就是**主线程**，
而 `sendExtended` 里的 `Socket.write` 在主线程会被 Android 拦下，抛
`NetworkOnMainThreadException`（它的 `message` 是 `null`，早先被 `catch` 静默吞掉，
现象就是"发送端什么都没收到、日志只有一句 `失败: null`"）。所以接收端是另起线程发的；
`status` 走会话自己的线程，从来没这个问题。反向消息的 `catch` 里也把异常**类型**一起打出来，
只打 `e.message` 遇到这类异常等于没打。

**向后兼容**：旧发送端读到 `0x7F` 会走 `onControl(127)`，其 `when` 没有该分支 → 直接忽略，
镜像链路的既有控制流完全不受影响；旧接收端则永远不会发扩展消息。

### 8.3 开投时的进度衔接

发送端在 `type=6` 之后立刻补一帧 `type=8 action=4`（值 = 本机当前播放位置）。接收端播放器
若尚未 `prepared`，会先把该位置暂存（`pendingSeekMs`），`onPrepared` 后立即应用 —— 于是
"手机上看到一半 → 投到平板"可以从同一位置接着播。
